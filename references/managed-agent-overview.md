ModelArk Managed Agents is a **prebuilt, configurable agent framework** provided by ModelArk. It runs on ModelArk\-managed infrastructure and is best suited for **long\-running, stateful asynchronous tasks with multi\-turn tool calls** .

To build a usable agent based on the model API, you need to implement common components yourself, such as AgentLoop, tool calls, context management, sandbox scheduling, checkpoint resume, and permission isolation. This usually takes 4 to 8 weeks and must be continuously adapted as models evolve. ModelArk Managed Agents delivers the full infrastructure stack at the agent layer. Developers only need to define agent behavior, send user events, and subscribe to result streams, while ModelArk handles all underlying complexity.

> ModelArk currently provides two ways to build agents based on Dola models: use the **model API** when you need fine\-grained control over the agent loop; use **Managed Agents** when you want ModelArk to host the agent and you want to focus on business logic. For detailed differences, see [Comparison with the model API](https://docs.byteplus.com/en/docs/ModelArk/2553713#vs_model_api).

<span id="core_concepts"></span>
# Basic concepts:

ModelArk Managed Agents is built around the following four concepts:


|Concept |Description |
|---|---|
|**Agent** |A versioned and reusable intelligent agent configuration asset. It defines roles, capabilities, behavior boundaries, and runtime rules of an agent, and serves as the template and baseline for all task runs. Create once and reuse across multiple sessions through `agent_id`. |
|**Environment** |The environment configuration for running a session, including network, preinstalled dependency packages, and environment variables. Referenced through `environment_id`. |
|**Session** |An agent instance that runs in an environment and is used to execute a specific task. Context, files, and state are isolated from each other. The same agent can start multiple parallel sessions. |
|**Events** |Atomic messages exchanged between the application and the agent, including user messages, thoughts, tool calls, tool results, and status updates. Persisted on the server in an append\-only way, supporting real\-time subscription and later replay. |


<span id="advantages"></span>
# Core benefits

<span id="vs_model_api"></span>
## Comparison with the model API

The **model API** is the atomic interface for accessing model capabilities. You need to implement the loop, parse tool calls, and maintain context yourself. It is suitable for scenarios that require **fine\-grained control** . In comparison, **ModelArk Managed Agents** is an encapsulated interface for accessing agent capabilities. It consolidates the common capabilities that previously had to be built at the agent layer into the platform.

<span id="no_longer_needed"></span>
### Parts you no longer need to implement yourself


|Before (model API + self\-built loop) |After (ModelArk Managed Agents) |
|---|---|
|Maintain the conversation history array and send the full history back to the model in each turn. |The session history is persisted on the server. You only need to send / subscribe to events. |
|Manual loop calls: model returns → parse `tool_use` → execute tool → append `tool_result` → call the model again |The platform has a built\-in AgentLoop that automatically drives the entire loop. When the agent finishes, it emits `session.status_idle`. |
|Build your own sandbox to execute code generated by the agent, and manage machines, containers, scaling, and cleanup yourself. |Each session comes with a sandbox. The platform hosts code execution, file read/write, and Bash commands, and releases resources when the task ends. |
|Develop your own context compression policy to avoid exceeding the context window. |Context is automatically compressed, and the Event API retains all content without loss. |
|Develop your own checkpoint and recovery mechanism for long\-running tasks. |Snapshots are automatically generated, and long\-running tasks natively support checkpoint resume. |
|Develop your own IAM, key injection, and runtime environment isolation. |Based on BytePlus IAM + zero\-trust credential isolation, keys do not enter sandbox processes. |


<span id="still_controlled"></span>
### Parts still controlled by users


* **Model configuration and system prompt** : The parameters remain unchanged. Only their position is moved into the agent definition.

* **Custom tools** : `input_schema` is still declared using JSON Schema. Now the user client can subscribe to the `agent.custom_tool_use` event and executes the tool itself.

* **Context injection** : You can still inject context through system prompts, skills, uploaded files, and other methods.

* **Interruption and guidance** : You can send extra user events to a session at any time to adjust the direction, or directly interrupt the current run.


<span id="when_to_use_model_api"></span>
### When you should still choose the model API

If your goal is **precisely to customize the agent loop itself** —for example, to explore new reasoning policies, build your own agent framework, or apply special rewrites to each `tool_use` step—the model API is more suitable. Managed Agents is designed for "directly obtaining a runnable agent", not for "building an agent engine".

<span id="vs_open_source_agent"></span>
## Comparison with open\-source agents

Mainstream open\-source agent runtimes, such as LangChain and OpenCode, make the agents runable, but it still requires significant investment to make agents stable, efficient, and valuable for business. ModelArk is not "adding an adapter layer for Dola models on top of an open\-source framework". Instead, it **builds the AgentLoop scheduling kernel from the ground up and performs deep bidirectional optimization with the native capabilities of Dola foundation models** . This is equivalent to equipping the model with a tailor\-made operating system, rather than running it broadly on general\-purpose hardware.


|Comparison dimension |ModelArk Managed Agents (native AgentLoop) |Open\-source agent runtime |
|---|---|---|
|**Model adaptation method** |Native bidirectional optimization with the full Dola model series |General prompt templates adapted to all models |
|**Reasoning completion rate** |Native chain\-of\-thought decomposition, checkpoint resume, and automatic context compression. |Long tasks can easily drift from expectations, cannot resume after interruption, and may lose context. |
|**Tool call** |Protocol\-level alignment with automatic validation / retry / parallel execution. |General JSON parsing. |
|**Long\-running tasks** |Native support for long\-running tasks, with automatic snapshot generation and on\-demand startup. |Fixed templates adapted to all scenarios, requiring self\-built sandbox scheduling. |
|**Integration cost** |Ready to use out of the box with zero adaptation cost. |Requires 4–8 weeks of adaptation with a long trial\-and\-error period. |


<span id="use_cases"></span>
# Use cases

ModelArk Managed Agents is best suited for workloads with the following characteristics:


* **Long\-running** : A single task needs to run for minutes to hours, involving multiple tool calls and iterative thinking.

* **Stateful** : Persist the filesystem, conversation history, and execution state across multiple interaction turns, with support for checkpoint resume.

* **Asynchronous execution** : After a task is started, the agent proceeds autonomously. The client only needs to subscribe to the event stream to get results.

* **Minimal infrastructure** : No need to build your own agent loop, sandbox, or tool execution layer.

* **Elastic calls** : Call volume has clear peaks and troughs, so you prefer pay\-as\-you\-go billing over always\-on resources.


Based on these characteristics, the following are typical business scenarios with validated PMF:


|Scenario |Repetition |Risk |Description |
|---|---|---|---|
|**IT ticket handling** |High |Low |Highly structured and highly templated, with high agent processing accuracy. |
|**Automatic report generation** . |High |Low |Fixed data collection and summary logic, making it easy to agentize. |
|**Supplier email handling** |Medium |Low |Clear classification and reply processes, suitable for rule\-based automation. |
|**Code review and documentation** |High |Low |R&D teams see direct benefits, with significant ROI. |
|**Initial sales lead screening** |Medium |Low |Automates CRM entry and frees up sales capacity. |


Teams that are using open\-source agents to build their own business workflows or stitching together agent capabilities through scripts can consider migrating to ModelArk Managed Agents for pilot validation.

<span id="workflow"></span>
# Workflow

From creation to business integration, ModelArk Managed Agents usually involves the following five steps:


1. **Create an agent** : Define the model, system prompt, and skills / tools / MCPs in the console or through APIs to obtain a stable `agent_id`, which can be reused by ID across multiple sessions.

2. **Create an environment** : Define the sandbox runtime environment, including preinstalled packages and environment variables, to obtain a stable `environment_id`.

3. **Start a session** : Create a session based on `agent_id` and `environment_id`.

4. **Send events and receive streaming responses** : Send user messages to the session as events. The agent autonomously executes tools and returns results as a stream through SSE (server\-sent events). The event history is persistently stored on the server and can be fully retrieved.

5. **Guide or interrupt** : While the agent is running, you can send extra user events at any time to guide it to adjust direction, or directly interrupt the current run.


The following two paths are available to get started:


* To quickly validate a prototype in a **visual** way, see [Quick start (console)](https://docs.byteplus.com/en/docs/ModelArk/2553715).

* To complete end\-to\-end integration directly with **code / APIs** , see [Quick start (code)](https://docs.byteplus.com/en/docs/ModelArk/2553714).

# Billing

Managed Agents is billed based on the sum of three items actually consumed during agent runs: tokens, agent runtime duration, and the number of tool calls. For details, see [Managed Agents billing](https://docs.byteplus.com/en/docs/ModelArk/1544106#ma_billing).
